# Правила разработки Taktera.Mail

## Контекст и границы

Taktera.Mail — быстрый и легковесный почтовый клиент Windows/macOS на C#, .NET 10,
Avalonia UI и CommunityToolkit.Mvvm. Windows — приоритетная платформа.
Текущее состояние — демонстрационный UI, минимальные Domain-модели, контракты
синхронизации, пустой проект Infrastructure и тесты Domain.
Читайте `README.md`, `docs/ARCHITECTURE.md`, `docs/AUDIT.md` и `docs/IMPLEMENTATION_PLAN.md`.
План описывает предложения, а не уже реализованные возможности.

- Работайте в отдельной ветке `codex/<описание>` или явно указанной пользователем.
- Перед изменениями проверяйте `git status`; сохраняйте чужие изменения.
- Не объединяйте изменения с `main` и не выполняйте push без поручения пользователя.
- Изменение границ слоев, добавление Infrastructure, выбор хранилища секретов,
  HTML-движка и новых транспортов сначала оформляйте как предложение/ADR и согласовывайте.
- До отдельного разрешения не подключайтесь к реальным почтовым аккаунтам,
  не запускайте OAuth-вход и не отправляйте реальные письма. Используйте фикстуры и локальные стенды.
- Не добавляйте фреймворки, сервисы и зависимости без конкретной необходимости.

## Архитектура и код

- Сохраняйте текущие ссылки: Desktop → Application → Domain и Infrastructure → Application.
  Начальная структура Infrastructure согласована; см. `docs/ADR-001-foundation.md`.
- Domain не должен зависеть от Avalonia, БД, MailKit, MimeKit или OAuth SDK.
- Application содержит сценарии и контракты; UI и детали внешних систем туда не переносите.
- Desktop отвечает за представление и MVVM; code-behind допустим для поведения представления.
  Не выполняйте сетевые запросы и SQL из View/ViewModel.
- При утверждении Infrastructure размещайте там реализации транспорта, MIME, SQLite и OAuth;
  наружу возвращайте модели приложения, а не типы сторонних библиотек.
- Используйте nullable-аннотации, понятные имена, обычное многострочное форматирование C#/XML.
  Не смешивайте массовое форматирование с функциональными изменениями.
- Для действий UI используйте команды CommunityToolkit.Mvvm; явно показывайте состояния
  загрузки, ошибки, пустого списка и отмены.
- Ввод-вывод выполняйте асинхронно с CancellationToken; избегайте `.Result`, `.Wait()`
  и `async void`, кроме обработчиков событий. Коллекции UI меняйте на UI-потоке.
- Освобождайте соединения, потоки и подписки; ограничивайте параллелизм и объемы загрузки.
- Даты храните с временной зоной/в UTC, форматируйте в UI. Не используйте отображаемые
  строки и Message-Id как единственный идентификатор сообщения.

## Безопасность и данные

- Не сохраняйте токены, пароли, содержимое писем и персональные данные в Git или логах.
- Секреты храните через утвержденный платформенный адаптер; SQLite не является хранилищем токенов.
- Не отключайте проверку TLS-сертификатов. Не встраивайте client secret в desktop-приложение.
- HTML писем и вложения считайте недоверенными: запрет скриптов и внешних ресурсов по умолчанию,
  проверка имен/путей, лимиты размера, никаких автоматических запусков вложений.
- SQL параметризуйте; синтаксис FTS-запросов валидируйте отдельно от SQL-параметров.
- Миграции БД должны сохранять данные; проверяйте восстановление после прерывания.
  Удаление аккаунта должно иметь явную политику очистки кеша, индекса и секретов.

## Проверка и завершение

Из корня репозитория:

```powershell
dotnet build Taktera.Mail.slnx --configuration Release --nologo
dotnet test Taktera.Mail.slnx --configuration Release --no-build
dotnet list Taktera.Mail.slnx package --include-transitive --vulnerable
dotnet run --project src/Taktera.Mail.Desktop
```

Если SDK установлен, но отсутствует в PATH, на этой Windows-машине используйте
`& 'C:\Program Files\dotnet\dotnet.exe'` вместо `dotnet`. Не меняйте окружение пользователя молча.

- Solution включает четыре основных проекта и `Taktera.Mail.Domain.Tests`.
  Сборка только Desktop не проверяет Infrastructure и тесты.
- Для отдельной проверки запускайте относящиеся к изменению проекты командой
  `dotnet test <путь-к-тестовому.csproj> --configuration Release`.
- Для синхронизации, миграций, поиска и отправки нужны тесты граничных случаев и сбоев;
  тесты не должны требовать личных аккаунтов или внешней сети.
- UI проверяйте на Windows: минимальный размер окна, длинные письма, клавиатура, DPI и пустые состояния.
  Совместимость macOS подтверждайте отдельной сборкой и проверкой на macOS.
- Не подавляйте предупреждения безопасности ради зеленой сборки. Фиксируйте причину и план устранения.
- В отчете укажите изменения, команды и результат проверок, оставшиеся ограничения.
  Успешная компиляция не означает успешную проверку UI или почтовых сценариев.
