# План полноценного почтового клиента

Дата: 13 октября 2026. Статус: частично согласованная начальная структура; остальное — план.
Пользователь согласовал Infrastructure, минимальные Domain-модели, интерфейсы синхронизации
и тесты; реализованный объем описан в [ADR-001](ADR-001-foundation.md).
DI, адаптеры, хранение и подключение реальных аккаунтов пока не реализованы и не согласованы.
Текущее состояние и проверка сборки описаны в [AUDIT.md](AUDIT.md).

## Цель и объем

Windows-first клиент с несколькими аккаунтами, папками, офлайн-чтением,
поиском, черновиками, ответом/пересылкой, вложениями и надежной очередью отправки.
После Windows — подтвержденная поддержка macOS. Базовый транспорт: MailKit IMAP/SMTP,
обработка сообщений: MimeKit, локальные данные: SQLite + FTS5, авторизация: OAuth2.
POP3, календарь, контакты, S/MIME, PGP и правила сервера — последующие отдельные задачи.
Microsoft Graph уже упомянут в README; его необходимость следует решить отдельно,
не добавляя одновременно второй транспорт в первый рабочий релиз.

## Решения, требующие согласования

1. Начальный граф Infrastructure → Application → Domain согласован и создан.
   Подключение реализаций к Desktop через DI остается будущим решением.
2. Выбрать SQLite-провайдер (кандидат Microsoft.Data.Sqlite), механизм миграций,
   размещение кеша и политику шифрования. Обычная SQLite не шифрует письма.
3. Утвердить OAuth-провайдеры первого релиза, регистрацию public client,
   redirect URI, scopes и платформенное хранилище секретов
   (Windows Credential Manager/DPAPI-адаптер и macOS Keychain).
4. Выбрать безопасный HTML-рендерер с учетом размера приложения и macOS.
   До решения поддерживать plain text, не подключать произвольный WebView.
5. Определить поддержку Microsoft 365 при отключенном tenant policy IMAP/SMTP:
   явно сообщать об ограничении или отдельно разрабатывать Graph-адаптер.

Каждое решение фиксировать коротким ADR: проблема, варианты, выбор, риски и критерии проверки.
До согласования допустимы документация и обсуждение контрактов без изменения графа проектов.

Этапы 0–1 выполнены частично: исправлена зависимость, добавлены solution, доменные модели,
контракты и тесты. CI, закрепление SDK, DI и функциональный offline UI еще впереди.

## Предлагаемое устройство

Domain: AccountId, FolderId, MessageId, адреса, флаги, локальные черновики и состояния отправки.
Application: сценарии получения списка/тела, поиска, синхронизации и отправки;
контракты хранилища, транспорта, авторизации, часов и секретов.
Infrastructure: MailKit, MimeKit, SQLite/FTS5, OAuth SDK и платформенные адаптеры.
Desktop: представления, команды и отображение состояний; без прямого SQL/IMAP.
Это границы ответственности, а не требование создавать интерфейс для каждого класса.

### Данные и поиск

- Таблицы Accounts, Folders, Messages, FolderMessages, Attachments, Drafts,
  Outbox, PendingOperations и SyncState; окончательная схема — после ADR.
- Локальный ID независим от сервера. Уникальность IMAP-записи:
  account + folder + UIDVALIDITY + UID. Message-Id может отсутствовать или повторяться.
  Связь с папкой позволяет учитывать Gmail labels и копии без предположения об одном UID на аккаунт.
- Хранить даты типизированно; адреса структурированно, флаги и checkpoint отдельно.
  Тела и вложения загружать по требованию; установить квоты и очистку кеша.
- SQLite: foreign keys, транзакции, версионируемые миграции, WAL и контролируемая очередь
  записи. WAL не отменяет необходимость учитывать единственного writer и SQLITE_BUSY.
- FTS5 индексирует тему, адреса и извлеченный текст; HTML сначала нормализуется.
  Предлагается external-content индекс с транзакционными триггерами, backfill и rebuild.
  Проверять фактическую поддержку FTS5 в поставляемой native SQLite на обеих ОС.
- Начать с unicode61; проверить русские и английские запросы, диакритику и префиксы.
  Морфологию не обещать. Пользовательский текст переводить в безопасный ограниченный
  FTS-синтаксис; параметры SQL сами по себе не предотвращают ошибки MATCH-грамматики.
- Поиск ограничивать аккаунтом/папкой, выдавать страницы с устойчивой сортировкой.
  Обновление, удаление и очистка аккаунта должны синхронно обновлять индекс.

### Синхронизация и MIME

- Сначала получать папки и порции заголовков; тела и вложения отдельно.
  Учитывать special-use папки, кодировки, multipart/alternative, inline CID,
  поврежденные MIME и ограничения размера/глубины разбора.
- На аккаунт — ограниченное число соединений; команды одного ImapClient сериализовать.
  Для команды завершать IDLE корректно, затем возвращаться к ожиданию; при отсутствии
  IDLE использовать polling с backoff/jitter и отменой.
- Хранить UIDVALIDITY, UID и MODSEQ при поддержке CONDSTORE/QRESYNC.
  При смене UIDVALIDITY пересоздавать серверное сопоставление, сохраняя локальные черновики.
  Без расширений выполнять сверку UID/флагов и удалений ограниченными порциями.
- Коммитить данные и checkpoint вместе; после сбоя повтор не должен создавать дубликаты.
  Offline-операции хранить отдельно, задавать правила конфликтов и повторного исполнения.
  Удаление сначала трактовать как перенос в корзину; expunge — отдельное явное действие.
- На остановке приложения отменять операции и корректно закрывать соединения.

### OAuth2 и защита

- Authorization Code + PKCE через системный браузер, state и допустимый loopback redirect;
  SDK провайдера предпочтительнее собственной реализации протокола. Desktop — public client.
- Для Microsoft рассмотреть MSAL; для Google — поддерживаемую библиотеку native OAuth.
  Токен с правильными audience/scopes передавать в MailKit через SASL XOAUTH2.
  Токен Graph нельзя считать взаимозаменяемым с IMAP/SMTP токеном.
- Refresh выполнять один раз одновременно на аккаунт; учитывать истечение, отзыв,
  ротацию и invalid_grant. Последнее переводит аккаунт в состояние повторного входа,
  а не запускает бесконечные повторы. Logout удаляет секреты и применяет выбранную политику кеша.
- Для Gmail IMAP/SMTP проверить scope mail.google.com, требования consent/verification;
  для Microsoft — delegated IMAP/SMTP scopes и политики tenant/SMTP AUTH.
  Регистрация приложений и разрешение провайдера — зависимости релиза, а не только код.
- Протокольные логи по умолчанию отключены; диагностика не содержит токенов и писем.
  TLS проверяется стандартно; удаленные изображения, скрипты и автоматическое открытие вложений запрещены.

### Отправка

MimeKit формирует текст/HTML, To/Cc/Bcc, вложения и threading-заголовки.
Черновик сохраняется локально до сети; очередь имеет состояния queued, sending,
sent, failed и unknown. Если соединение оборвалось после передачи SMTP DATA,
результат может быть неизвестен: не повторять отправку автоматически и не обещать exactly-once.
Сохранение в Sent/IMAP APPEND — отдельный шаг: его сбой не должен повторно отправлять письмо.
Учитывать, что провайдер может сам сохранять Sent. Bcc не должен утекать получателям в заголовках.

## Проверки производительности и надежности

Предварительные цели для согласования, не измеренные свойства текущего приложения:
на зафиксированном Windows x64 стенде с SSD и 16 ГБ RAM холодный запуск до списка ≤2 с,
поиск p95 ≤300 мс на 100 000 индексированных писем, idle working set ≤200 МБ.
Отдельно фиксировать размер тел корпуса, состояние кеша, размер дистрибутива и CPU idle.
Виртуализировать список, не загружать весь ящик в ObservableCollection,
использовать пагинацию и bounded queues. Оценить HTML-движок по этим же метрикам.

Unit: сценарии/состояния/отмена; integration: реальная временная SQLite/FTS5,
миграции и локальные IMAP/SMTP стенды; UI smoke: Windows и macOS.
Сценарии сбоев: потеря сети, занятая/переполненная БД, завершение процесса между записью
и checkpoint, отозванный токен, поврежденный MIME и неоднозначный SMTP-результат.
CI не использует личные почтовые аккаунты. Перед релизом — контролируемые provider smoke tests
по отдельному разрешению и проверка удаления всех данных аккаунта.

## Первичные источники

Сверены 13 октября 2026; перед реализацией повторно проверить версии и политики провайдеров.

- [MailKit ImapClient](https://mimekit.net/docs/html/T_MailKit_Net_Imap_ImapClient.htm) и [IdleAsync](https://mimekit.net/docs/html/M_MailKit_Net_Imap_ImapClient_IdleAsync.htm): соединение, сериализация команд и IDLE.
- [SQLite FTS5](https://www.sqlite.org/fts5.html): external-content, триггеры, rebuild и токенизация.
- [Microsoft desktop authentication flows](https://learn.microsoft.com/en-us/entra/identity-platform/authentication-flows-app-scenarios): Authorization Code + PKCE.
- [Microsoft OAuth для IMAP/SMTP](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth): scopes и XOAUTH2.
- [Google OAuth для desktop](https://developers.google.com/identity/protocols/oauth2/native-app): public client, PKCE и redirect.
- [Gmail XOAUTH2](https://developers.google.com/gmail/imap/xoauth2-protocol): механизм аутентификации IMAP/SMTP.
